MiniCDN Project Brief for the Team

Project rationale, USP, implemented changes and dashboard guide
1 October 2026

We are building a small, observable content delivery network to study how caching and routing reduce origin work while keeping content available and fresh. The current system provides a working baseline across three edge nodes. We will use controlled experiments to assess each research improvement.

Why we are building this project

A website that serves every asset from one origin repeats network transfers and concentrates request load at a single service. Edge caches can reuse responses, but they introduce engineering trade-offs: popular content can overload one edge, concurrent misses can overwhelm the origin, and missed purges can leave old content behind.

MiniCDN gives us control over those mechanisms. We can inspect the request path, change one policy at a time, simulate failures, and measure the effect. The project combines HTTP, concurrency, distributed registration, cache correctness and observability in a system small enough to run locally.

The project USP

MiniCDN is a reproducible CDN research platform for reducing duplicate origin work and evaluating the balance between cache locality, edge load and content freshness.

The first implemented contribution is cache-fill coordination. When many clients request the same uncached static object, one request fills the edge cache and waiting requests reuse it. The broader research direction adds load-aware routing and invalidation recovery, with explicit measurements of both benefits and overhead.

The techniques are established in industry and research. Our contribution should be the implementation choices, their integration into this system, and reproducible experimental comparisons. We should describe adaptive routing and gossip invalidation as planned until they are implemented and evaluated.

A concise project explanation

“We are building a small CDN with three edge caches and a health-aware router. We already reduce duplicate origin fetches during concurrent cache misses. Next, we will investigate how to distribute skewed traffic and recover missed cache invalidations, using Prometheus and Grafana to compare each improvement with a fixed baseline.”

How the current system works

The router selects a healthy edge using consistent hashing on the URL path. Each edge stores successful cacheable GET responses in memory. A fresh response is a HIT; otherwise the edge contacts the origin and may populate the cache. Edges register periodically with the Redis-backed control service, which also broadcasts exact-key purge requests.

Evidence collected so far

The barrier-controlled regression sends 32 simultaneous requests for one cold object. Without coordination it observes 32 origin fetches; with coordination it observes one. This passed in 10 repeated runs, equivalent to a 96.9% reduction in origin fetches for this specific test. It does not establish a general latency or production performance improvement.

The full test suite passed with native Windows Go 1.27.0 and the project Go 1.21 container toolchain. Linux race checks also passed. A separate dashboard demonstration completed 640 requests with no errors, 626 HITs and 14 MISSes; Prometheus recorded 208 coalesced requests. These are local demonstration observations, not a controlled performance benchmark.

Changes added to the project

Per object cache fill coordination

A new per-key gate lets one request perform a cache fill while other requests for that key wait. After acquiring the gate, each request rechecks the cache. Different keys can proceed independently, canceled waiters can leave, and unused gates are removed. Set COALESCING_ENABLED=false on an edge to run the independent-fetch baseline.

Cache correctness and purge ordering

An internal Peek checks freshness without counting another client lookup. Requests with Authorization, Cookie, Range or explicit Cache-Control bypass shared caching. Responses with Vary or Set-Cookie are excluded from storage until variant-aware keys are implemented.

Exact-key purge waits for coordinated fills before deleting the cached object, preventing an earlier coordinated fill from repopulating that key after purge acknowledgement. This protection is scoped to coordination mode; durable missed-purge recovery and query-variant or prefix purging still need work.

Metrics and regression tests

cdn_origin_requests_total counts origin fetch operations, including misses and bypasses. cdn_coalesced_requests_total counts initial misses that reused another request's cache fill. Followers retain X-Cache: HIT, while the separate counter identifies the coordination benefit.

Tests cover the baseline comparison, canceled followers, independent-key progress, gate cleanup and conservative response cacheability. Go was installed and the existing Docker engine was started so these checks could execute.

Dashboard and team documentation

The dashboard now filters health and purge requests out of content traffic, exposes origin and coalescing counters, and adds cumulative response counts and an estimated edge P95 latency panel. Datasource references are aligned with Grafana provisioning. The repository also includes the research roadmap, development commands and a bounded metrics-demo script.

Limits of the first increment

The origin response is still read completely into memory. There is no streaming fan-out, disk persistence or object-size limit. The fill gate remains held while the leader writes its response, so a slow client can delay followers. Uncacheable and failed responses are fetched independently by waiting callers, potentially serially. These are concrete topics for the next increment.

Relevant files: cmd/edge/coalescing.go, cmd/edge/main.go, cmd/edge/coalescing_test.go, pkg/cache/cache.go and configs/grafana/provisioning.

To generate activity, run node scripts/metrics-demo.mjs from the project root while watching Grafana with a five-second refresh. It sends 640 requests over roughly 20 seconds. Rates return toward zero after traffic stops; that is expected. Cumulative counters reset when their edge restarts. A short test with fast origin responses may have fewer coalesced followers because some clients arrive after the cache is already warm.

The P95 chart estimates the latency below which 95% of edge requests complete. Histogram buckets limit precision, especially for very fast local requests. Use a client-side benchmark for end-to-end P95 and P99. The small demonstration produced 480, 80 and 80 requests across the three edges; hashing a few URLs does not guarantee equal request counts.

Next implementation stages

  1. Finish the cache foundation: bounded storage, variant-aware keys, expired-object revalidation and shorter fill-gate lifetime.
  2. Compare hash routing, round robin and adaptive load-aware selection under uniform and skewed workloads.
  3. Add durable invalidation versions and recovery after an edge disconnects or misses a purge.
  4. Choose one extension such as hot-object replication, peer caching or prefetching, with an explicit overhead budget.

The separate phase-deliverables document will determine the final academic milestones. Team research source: Research gaps mini cdn. Supporting references: Go singleflight, Bounded-load hashing, Grafana provisioning and Prometheus histograms.
